# 3D LUT 뱅크 덤프 분석 (2026-10-25)

방법 B (docs/research/2026-10-23-lut-firmware-analysis.md 3장) 의 첫 카메라 시험. 읽기만 했다.

## 1. 시험

M 모드, 텔넷, 펌웨어 1.12. nxmem (sd/nx500ex/bin/nxmem) 으로 0x810c3500 부터 0xcf300 (848,640) 바이트를 세 번 떴다.

| 덤프 | 상황 |
| --- | --- |
| lut_a.bin | 그대로 |
| lut_b.bin | st app mode m 으로 모드 재진입 뒤 |
| lut_c.bin | 화면 마법사 비비드, WB 3200K 로 바꾼 뒤 |

같이 본 것: st cap iq ipc proc sysinfo 에 "3D LUT 1" (켜짐), 대비/채도/선명도 10, color_space 0. /dev/mem 접근은 멈춤 없이 바로 됐다.

덤프는 dumps/lut/lut_a.bin 에 둔다 (b, c 는 LUT 영역이 a 와 같아서 레포에 넣지 않음).

## 2. 결과

### 뱅크는 고정 데이터

세 덤프는 0x810c3500 부터 0x8118dac4 (마지막 표 끝) 까지 완전히 같다. 다른 곳은 그 뒤 0x8118db94 ~ 0x8118dbb4 의 32바이트뿐 (표 바깥의 작업 변수). 모드 재진입도, 화면 마법사와 WB 변경도 뱅크 내용을 바꾸지 않는다. 펌웨어 분석대로 뱅크는 부팅 때 채워지고 상황에 따라 골라 쓰는 것이다. 덮어쓰면 다음 적재 때 반영될 가능성이 높다.

### 배치: 17x17x17 표 42개, 두 구간

표 하나는 4,913 항목 x 4바이트 = 19,652 바이트, 뱅크 간격 0x4d00 (19,712), 표 뒤 60바이트는 패딩.

| 구간 | 표 | 주소 | 비고 |
| --- | --- | --- | --- |
| A | 0 ~ 19 | 0x810c3500 + k x 0x4d00 | 표 19 끝 0x811238c4 |
| 틈 | | 0x811238c4 ~ 0x81123d00 (1,084 바이트) | 색상 회전 행렬 표 등 (아래) |
| B | 20 ~ 41 | 0x81123d00 + (k-20) x 0x4d00 | 표 41 끝 0x8118dac4 |

펌웨어의 고정 뱅크 4개는 표 12 (0x810fd100), 13 (0x81101e00), 14 (0x81106b00), 17 (0x81115200) 이다. 구간 B 의 주소는 구간 A 의 0x4d00 격자에서 0x400 밀려 있으므로, 펌웨어 선택 함수의 주소 표를 읽을 때 이 점을 감안해야 한다.

### 항목 형식: (c0, c1, c2, 0) 8비트, c0 이 가장 빠른 축

- 4바이트 중 넷째는 전부 0.
- c0 은 가장 안쪽 축(항목 1칸)에서, c1 은 가운데 축(17칸)에서, c2 는 바깥 축(289칸)에서 단조 증가한다. 42개 표 모두 세 축 단조 비율 1.00.
- 입력 격자 i 번째 칸 = i x 255 / 16 (0, 16, 32, ... 255) 로 보면 항등에 가까운 표가 입력을 그대로 돌려준다.

### 색 공간: YCbCr, 항목 = (Cr, Cb, Y, 0)

RGB 가 아니다. 근거:

1. 42개 표 모두에서 입력 (128, 128, Y) 의 출력이 정확히 (128, 128, Y') 이다. 색차가 중립이면 밝기와 무관하게 중립으로 남는다. RGB 표라면 (128,128,Y) 는 회색이 아니라 파랑 축이라 이런 보존이 나올 이유가 없다.
2. 항등에 가까운 표 13 에서 c2 가 208 이하이면 c0, c1 이 그대로 통과하고, 208 을 넘으면 c0, c1 이 128 쪽으로 눌린다 (Y 224 에서 0.9배, 240 에서 0.7배, 255 에서 0.45배). 밝은 부분 채도 억제라는 흔한 처리다. RGB 로 읽으면 "흰색을 (185,185,255) 청회색으로" 가 되어 말이 안 된다.
3. 두 해석으로 시험 이미지를 렌더링하면 (dumps/lut/compare_sheet.png, tools/lut/apply_lut.py) YCbCr 해석의 표 13 은 원본과 같고 RGB 해석은 흰색이 연보라가 된다. 비교판의 t13_ycc, t12_ycc 는 (Cb, Cr, Y) 해석, t13_yccswap, t12_yccswap 이 확정된 (Cr, Cb, Y) 해석이다.
4. 표 사이의 틈에 cos/sin 쌍 (222/128, 235/104, 243/79, 250/53, 255/27, 256/0, ...) 이 6도 간격으로 +30도에서 -30도까지 놓인 2x2 회전 행렬 표가 있다. 색차 평면의 색상 회전용이다.

c0 = Cr, c1 = Cb 는 쓰기 시험 (5장) 으로 정했다. 변환 계수(BT.601 인지, 전범위인지)는 아직 확인 대상이다. 미리보기 도구는 BT.601 전범위를 가정한다.

### 다섯 가족

검정 모서리 (0,0,0 입력) 와 흰 모서리 (255,255,255 입력) 의 출력으로 묶으면 다섯 가족이다. 같은 가족 안에서도 내용은 조금씩 달라 (md5 전부 다름) 색온도나 밝기별 변형으로 보인다.

| 가족 | 표 | 검정 -> | 흰 -> | 성격 |
| --- | --- | --- | --- | --- |
| 1 | 0, 3, 6, 9, 20, 21, 26, 27 | (8, 8, 16) | (182, 182, 254) | Y 를 +16 올리고 254 에서 자름. 색차 이득 중간 1.05 ~ 1.09, 밝은 곳 0.7 |
| 2 | 1, 4, 7, 10, 22, 23, 28, 29 | (16, 16, 16) | (178, 178, 254) | 가족 1 과 비슷, 어두운 곳 색차를 더 누름 |
| 3 | 2, 5, 8, 11, 24, 25, 30, 31 | (1, 1, 1) | (185, 185, 254) | Y 그대로, 색차 이득 약간 |
| 4 | 12, 14, 15, 16, 32, 34, 36, 38, 40 | (21, 0, 13) | (171, 190, 245) | 색이 있는 표. 색차 이득 0.91, 색상 +8도 회전, Y 곡선 약간 다름. 노랑이 옅어지고 전체가 부드러운 스타일 |
| 5 | 13, 17, 18, 19, 33, 35, 37, 39, 41 | (0, 0, 0) | (185, 185, 255) | 항등에 가깝고 밝은 곳 채도 억제만. 색차 이득 1.0 ~ 1.16 |

구간 A 의 0 ~ 11 은 가족 1, 2, 3 이 네 번 반복, 12 ~ 19 는 가족 4, 5 가 섞여 있다. 구간 B 의 20 ~ 31 은 가족 1, 2, 3 이 둘씩 짝으로, 32 ~ 41 은 가족 4, 5 가 번갈아 있다. 어느 표를 언제 쓰는지(화면 마법사별인지, 색온도별인지, 라이브 뷰와 정지 사진이 다른지)는 펌웨어 선택 함수 (0x80383800, 0x80382b30) 를 이 주소 표와 맞춰 읽거나 쓰기 시험으로 알아낸다. 고정 뱅크 네 개 가운데 셋 (13, 14, 17) 이 가족 4, 5 라는 것이 단서다.

### 틈 블록 (0x811238c4 ~ 0x81123d00)

16비트 정수 행렬들. 앞쪽은 2x2 색상 회전 행렬 11개 (cos, sin 을 256 배로, +30도부터 -30도까지 6도 간격). 그 뒤 3x3 행렬 여럿 (대각 0x0100 = 1.0 근처의 작은 보정값), 마지막은 0. 3D LUT 와 직접 관계는 없지만 색차 평면 처리가 이 근처에 모여 있다는 뜻이다.

## 4. 쓰기 시험 (같은 날, 사용자 실기)

M 모드, 화면 마법사 표준, RAW+초고화질. 시험용 표는 표 13 에서 만들었다 (dumps/lut/write_test/, 덤프에서 재생성 가능).

| 순서 | 한 것 | 결과 |
| --- | --- | --- |
| 1 | 표 13 에 같은 값 다시 쓰기 (nxmem w), 다시 읽기 | 멈춤 없음, 값 일치. 쓰기 가능 |
| 2 | 표 13 을 흑백 표 (Cr, Cb 전부 128) 로, st app mode m, 반셔터, 촬영 | 변화 없음 |
| 3 | 영역 전체를 원본으로 되돌린 뒤 표 12, 13, 14, 17 을 하나씩 흑백 표로, mode m, 반셔터 | 표 17 (0x81115200) 에서만 반셔터 뒤 화면이 흑백. 12, 13, 14 는 변화 없음 |
| 4 | 표 17 을 c0 출력 뒤집은 표로, 반셔터 | 파랑이 핑크, 빨강과 핑크가 초록 계열. Cr 을 뒤집은 결과와 일치 -> c0 = Cr |
| 5 | 그 상태로 촬영, 재생 | 사진도 같은 반전. 정지 사진 JPEG 도 표 17 을 쓴다 |
| 6 | 표 17 을 c1 출력 뒤집은 표로, 반셔터 | 파랑이 초록, 핑크는 핑크, 주황이 진한 핑크, 연두가 파랑. Cb 를 뒤집은 결과와 일치 -> c1 = Cb |

정리:
- 화면 마법사 표준의 라이브 뷰와 JPEG 는 둘 다 표 17 을 쓴다 (고정 뱅크 4개 중 넷째).
- 적재는 반셔터 때 일어난다. st app mode m 만으로는 안 바뀐다.
- 항목 = (Cr, Cb, Y, 0).
- 복구는 영역 전체에 원본 덤프를 다시 쓰거나 전원을 껐다 켜면 된다 (RAM 뿐).

모르는 것: 다른 화면 마법사(비비드 등)와 다른 밝기/색온도에서 어느 표로 바뀌는지. 필요하면 같은 방법(한 표씩 흑백)으로 찾는다.

42개 전부로 바꾼 뒤 재시험 (같은 날):

| 한 것 | 결과 |
| --- | --- |
| 전원 켜기 (세피아 켜 둔 상태) | 세피아로 시작, 찍은 사진도 세피아 |
| 흑백 LUT, 촬영 | 사진 흑백 |

## 6. 변환 모델 검증 (같은 날)

타사 .cube 가 의도대로 나오려면 격자 모델과 YCbCr 변환이 맞아야 한다.

격자: 순정 항등 표가 0, 16, 32, ..., 240, 255 (노드 9 가 144. i x 255/16 이면 143) 이므로 하드웨어는 입력의 위 4비트를 색인, 아래 4비트를 분수로 쓰는 17점 격자다. 노드 i = 입력 i x 16, 노드 16 = 256 (닿지 않는 값, 밖으로 민 값을 둔다). cube2bank.py 가 이 모델로 만든 순수 항등 표는 순정과 같은 모양이다.

변환: lutcal.sh 로 모니터 색표를 순수 룩 8장 (항등, 색상 +30도, 채도 1.6, 채도 0.5, R 감마 0.7, G 감마 1.3, B 감마 1.5, 전체 감마 0.75) 으로 찍고, lut_verify.py 가 항등 사진의 24칸에서 각 룩의 결과를 네 모델로 예측해 실제 사진과 비교했다 (dumps/lut/cal1_verify.txt, 칸 위치 cal1_patches.png). 흰 칸 RGB 최대 219 (Y 200 아래, 순정 밝은 곳 억제 바깥).

| 모델 | 7개 룩 평균 ΔE76 | 색상 +30도 룩 |
| --- | --- | --- |
| BT.601 전범위 | 1.25 | 1.30 |
| BT.601 제한 범위 | 2.46 | 1.35 |
| BT.709 전범위 | 2.30 | 4.78 |
| BT.709 제한 범위 | 3.05 | 4.70 |

BT.601 전범위로 확정. 색상 회전은 행렬(601 과 709)을, 채널 감마는 범위(전범위와 제한)를 가른다. 남는 오차는 룩마다 평균 0.5 ~ 1.3, 전체 감마 0.75 만 2.2 (어두운 칸, Y 축 17점 보간과 JPEG 압축). 눈으로는 구분 못 하는 수준이다.

한계: 하드웨어 격자가 17점이라 급한 룩은 보간 오차가 남는다 (색상 30도 회전 룩에서 PC 계산과의 차 RGB 평균 1.5, 최대 8). 어떤 방법으로도 이 아래로는 못 내려간다.

## 7. 레시피 묶기와 공개 LUT (같은 날)

- 레시피 = WB + 화면 마법사 (선명도, 큰 대비와 채도) + LUT (색의 모양). recipes.txt 12번째 칸에 LUT id. film.sh 가 lut.sh 를 quiet 로 불러 같이 쓰고, 레시피 끄기나 LUT 없는 레시피로 바꾸면 레시피가 켰던 LUT 만 끈다 (conf/lut_by_film 표식). 세피아, 셀레늄 토닝 복귀 (채도 0 + 토닝 LUT). Metropolis, Polaroid 600, SX-70, Pro 160NS, 크로스 프로세스, 바랜 인화에 LUT 를 더하고 화면 마법사 값을 조금 줄였다 (LUT 가 맡는 몫만큼). 실제 장면 확인은 남아 있다. 실기 (같은 날): 세피아 레시피가 갈색 흑백 + 팝업 "+ LUT", 레시피 끄기로 복귀, 회사별 LUT 메뉴와 촬영 정상, 메뉴에서 직접 고른 LUT 는 레시피를 바꿔도 유지. 모두 의도대로.
- 색표 재확인 (같은 날): 비교 촬영 (목록) 9장은 LUT 가 꺼진 채 찍혔다 (series.sh 가 LUT 칸을 몰랐음. 이제 목록 10번째 칸으로 LUT 를 켜고 찍고 끝나면 되돌린다). 화면 마법사만 적용된 그 사진에 PC 에서 레시피 LUT 를 얹어 (카메라 모델 ΔE 1 수준이라 예측이 믿을 만함) 완성 레시피를 재고 다듬었다: SX-70 은 중간 톤 자홍 틴트에 파랑이 섞여 회색이 b -1.8 로 차가웠던 것을 (0.025, -0.015, -0.005) 로 바꿔 a +8/b +1.6 따뜻한 자홍으로, Polaroid 600 섀도 녹색 a -6.7 -> -3.8, 셀레늄 섀도 a +8/b -8 -> +5/-5, Metropolis 탈색 시작을 35도로 당겨 노랑 채도 0.82 -> 0.73, 크로스 프로세스는 날아간 칸 9 라 화면 마법사 채도 12 -> 11, 대비 14 -> 12 (재촬영 필요). 세피아는 회색 b +16 ~ +20 (목표 +12 ~ +20), Pro 160NS 와 바랜 인화는 의도대로.

- 촬영이 끝난 뒤 화면에 마지막 룩이 남았다: series.sh 의 끝처리가 모드 재진입 직후 LUT 를 되돌려 반셔터 주입이 먹지 않은 것. LUT 를 먼저 되돌리고 재진입 뒤 반셔터를 한 번 더 넣도록 고침.
- 사용자 LUT (같은 날): 웹 변환기 https://nr2bj.github.io/nx500ex/ 의 zip 을 그대로 lut/user 에 넣고 전원을 켜니 풀리고 (boot.log "unzipped ..., user luts: 1") 메뉴 LUT > 사용자 > 에 보이며 누르면 적용됨. 실기 확인.
- MF 에서는 반셔터로 적재가 안 된다 (사용자 실기). 반셔터의 AF 시작이 라이브 뷰 파이프라인을 다시 초기화하면서 LUT 를 적재하는 것으로 보인다. 1차 후보 (luttrig.sh): 반셔터 주입, 모드 재진입, AEL, capt mf 토글, 드라이브, 화면 마법사 토글은 안 되고, 재생 화면에 갔다가 촬영 화면으로 돌아올 때와 사진 한 장 찍을 때는 된다 (라이브 뷰 재구성). common.sh lut_reload 가 반셔터 뒤 재생 왕복을 한다.
- 주의: 2차 후보를 한 번에 돌리다 촬영 서비스가 멈췄다 ("Cann't execute capture command over MCB", 버튼과 전원 무반응, 배터리 분리로 복구). 팝업은 7번까지 떴고 촬영 명령은 5번 "다이얼은 M 인데 st app mode p" 직후부터 실패했으므로 다이얼과 다른 앱 모드로 보내는 것이 원인이고, 마지막 st cap capt stop 이 프리징을 굳힌 것으로 본다. 금지: 다이얼과 다른 st app mode, st cap capt stop. st cap iq af mv 도 렌즈 스위치 MF 에서는 쓰지 않는다. 3차 (luttrig3.sh) 는 한 번에 하나씩, 안전한 후보만: AF 모드 재설정, LCD 껐다 켜기, 화면 터치 뒤 반셔터 모두 안 됨. 결론: 라이브 뷰를 다시 세우는 동작 (재생 왕복, 촬영) 외에는 적재가 없다. MF 에서는 재생 왕복 (약 2초) 으로 확정.
- 포커스 모드 이름: st cap capdtm getusr AFMODE -> "UserData is AFMODE_MANUAL (0x70003)" (MF, 렌즈 스위치 MF 포함). FOCUSMODE 는 없는 이름. common.sh focus_is_af 가 AFMODE 를 읽어 MANUAL 이 아니면 AF 로 본다. 실기 (2026-10-26): AF 에서는 반셔터만으로 바로, MF 에서는 재생 왕복 뒤 적용. 끄기도 같음.
- 더 나은 재적재 (2026-10-26, 8장의 metol 문서에서 본 방법을 실기로 확인): "OLED 색" 설정 (st cap capdtm setusr OLEDCOLOR, 끄기 0x6c0000, 켜기 0x6c0001. 이름 값은 Invalid argument) 을 반대로 바꿨다 되돌리면 MF 에서도 즉시, 끊김 없이 적재된다. common.sh lut_reload 가 이것을 기본으로 쓰고 (바꾼 뒤 값이 돌아왔는지 확인), OLEDCOLOR 를 못 읽을 때만 반셔터와 재생 왕복으로 간다. LUT 적용 경로 완료.
- 색 공간: AdobeRGB 로 찍으면 라이브 뷰가 다른 표 (14, 12) 를 고르지만 42개 전부 바꾸므로 LUT 는 먹는다. 다만 LUT 와 레시피는 sRGB 영상 기준으로 만든 것이라 AdobeRGB 에서는 채도가 조금 다르게 나온다. sRGB 권장. RAW (압축 방식 무관) 는 LUT 앞에서 빠져나가 영향 없음 (RAW 안의 미리보기 JPEG 는 영향).

## 10. 로그 입력용 LUT 와 다른 형식 (2026-10-26)

원래 "안 됨" 이던 종류를 변환기 쪽 계산만으로 되게 했다 (카메라 쪽 변경 없음).

- 로그 입력용 LUT (V-Log, S-Log3 (S-Gamut3.Cine, S-Gamut3), F-Log, F-Log2, N-Log, Canon Log 3, ARRI LogC3, LogC4) 와 선형 입력용, HLG, PQ: sRGB -> 역감마 -> 선형 -> 노출 (2^ev) -> 색 영역 행렬 -> 로그 곡선 -> LUT. 곡선은 제조사 공개 수식, 행렬은 colour-science 0.4.7 로 sRGB 선형 -> 각 색 영역 (D65, CAT02) 을 유도. tools/lut/inspace.py, inspace_test.py (colour-science 와 전부 일치). 근사인 이유: JPEG 는 톤이 눌리고 255 에서 잘려 로그의 하이라이트 여유가 없음. 흰색 1.0 이 V-Log 0.599 (90% 흰색 자리) 로 가 결과 흰색이 조금 가라앉을 수 있어 노출 보정 (스톱) 을 둠.
- 형식: .3dl (Autodesk, 빨강이 가장 느림, 정수 비트 깊이 추정 또는 Mesh 줄), .vlt (Panasonic VariCam, 12비트 정수, .cube 순서), .csp (Cinespace, 채널별 프리 LUT 를 선형 보간으로 먼저 적용). 1D cube 와 LUMIX Lab 태그는 앞서.
- 입력 공간 추정: LUMIX Lab 태그 (VLOG -> vlog, 그 외 -> srgb), 파일 이름 (slog3, vlog, flog2, flog, nlog, clog3, logc4, logc, hlg, pq, linear), DOMAIN 이 0~1 밖이면 linear. 페이지에서 고칠 수 있다.
- 검증: web/convert.js 와 cube2bank.py 가 vlog, slog3cine, logc4 (노출 +0.5), .3dl, .vlt, .csp 여섯 경우 모두 구간 A, B 바이트 일치 (web_test.js).
- 이름도 태그도 없는 LUT 의 입력 공간 판별 (inspace.detect_space, convert.js detectSpace): 회색 램프 12점과 색 패치 8개를 후보 공간 10개 (srgb, vlog, slog3cine, flog, flog2, nlog, clog3, logc3, logc4, linear) 로 각각 넣어 출력이 입력과 가장 비슷한 공간을 고른다 (오차 = 회색 밝기 RMS + 0.5 x 색 패치 RGB RMS, 회색이 뒤집히면 +0.5). 로그용 LUT 에 sRGB 를 그대로 넣으면 대비가 폭주해 오차 0.12 이상, 맞는 공간이면 0.01 안팎. 합성 "로그 -> 709" 변환 LUT 여섯 종 (colour-science 의 디코딩으로 만든 것) 전부 정답, 완성 영상용 룩 (세피아, 채도, 항등) 은 srgb. 색 패치 없이 회색만으로는 C-Log3 가 N-Log 로 잘못 잡혔다. 로그끼리의 확신은 1위와 2위 차이로 "높음/낮음" 을 보이고, 이름 힌트가 있으면 그쪽을 우선하되 내용과 어긋나면 주의를 띄운다.
