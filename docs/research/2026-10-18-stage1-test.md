## 알게 된 것

- dfmsd 는 nx_cs.adj 의 shell script 경로가 약 32자를 넘으면 실행하지 않는다. 31자는 동작, 34자는 실패. 커뮤니티 패키지는 모두 28자 이하를 썼다.
- 블루투스 서비스 시작부터 keyscan 의 auto 스크립트 실행까지 약 1초. 지연의 대부분은 카메라가 블루투스를 시작하기까지의 시간이다.

- 켤 때마다 블루투스가 다시 시작되므로 SD 의 keyscan 도 매번 다시 올라온다. keyscan 을 내장에 둘 필요가 없다 (2절 가정 확정).
- 두 번째 측정(18:03~18:05) 로그: boot.sh 는 cgroup systemd:/system.slice/dbus.service 안에서 실행되고 freezer 는 최상위(/)다. bluetoothd 가 D-Bus 로 시작되기 때문이다. 블루투스 서비스에 묶이거나 얼려지지 않으므로 "블루투스 OFF 시 freezer 로 정지" 가설은 철회.
- 두 번째 측정에서는 설정에서 켠 블루투스를 다시 꺼도 조합키가 동작했다 (18:04:40, 18:04:51). 첫 측정에서 조합키가 멈췄던 현상은 재현되지 않았고 원인 미상.
- 18:04:56 의 boot.sh 는 keyscan 시작 여부 기록 전에 끝났다 (직후 전원을 끈 것으로 추정).
- EV_S1.sh 의 진단은 pidof 가 없어 실패했다. /proc 을 직접 읽도록 수정했다.
- 결론: 켤 때 블루투스가 켜져 있으면 모드가 올라온다는 것만 보장한다. 블루투스 OFF 시 동작은 보장하지 않는다. 기능별 켜기/끄기는 메뉴 체크박스로 한다.

## keyscan 판정 순서 확인 (2026-10-19)

가설: "반셔터 더블클릭 판정이 EV 눌림 상태를 해제해 조합키가 무시된다" (상류 keyscan.c 기준).

실기 결과: 반셔터 후 1초 안에 EV+반셔터 켜짐, 2~3초 뒤 켜짐, EV 를 누른 채 반셔터 두 번 모두 켜짐. 가설 기각.

원인: 우리가 쓰는 NX-KS keyscan 바이너리(md5 3bb23225...)는 상류 keyscan.c 보다 새 버전이다. 디스어셈블(llvm-objdump, 0xb2e8~0xb5dc) 결과

| 항목 | 상류 keyscan.c | NX-KS keyscan 바이너리 |
| --- | --- | --- |
| 같은 키 1초 내 두 번 (더블클릭) | X_X 스크립트 실행, EV 눌림 상태 해제 | X_X 스크립트 실행, EV 눌림 상태 유지 |
| EV 누른 채 다른 키 (조합) | EV_X 실행 후 EV 눌림 상태 해제 | EV_X 실행, EV 눌림 상태 유지. EV 를 누른 채 여러 번 가능 |
| EV 눌림 상태 | EV 누름 1, 뗌 0 | 같음 (키 173, 150, 42) |
| 스크립트 실행 | system() 동기 실행 | 같음 (0xa5dc) |

따라서 keyscan 의 판정 순서로는 첫 측정의 이상 현상이 설명되지 않는다. keyscan2 를 만들 때는 상류 소스가 아니라 이 바이너리의 동작을 기준으로 한다.

첫 측정 이상 현상의 현재 상태

- 기각된 가설: 블루투스 OFF 시 freezer 정지, keyscan 의 더블클릭 판정 순서.
- 사실: 그 순간 keyscan 은 살아 있었다. 이후 블루투스 OFF 직후를 포함한 모든 시도(10회 이상)에서 재현되지 않았다.
- 남은 후보: 전원 ON 직후 관찰된 SD Input/output error 처럼 SD 가 순간적으로 접근 불가였다면 keyscan 은 스크립트를 찾지 못해 조용히 아무것도 하지 않는다. 입력 타이밍(EV 를 반셔터보다 늦게 누름 등)일 가능성도 있다. 재현 없이는 구분할 수 없다.
- 대응: 단계 2 부터 SD 에 debug 파일이 있으면 감시 기록(mon)이 켜지도록 넣어, 다시 발생하면 그 순간의 상태를 잡는다.

## 재생 화면 묶기: 순정 연사의 묶음 정보 (2026-10-19, 펌웨어 분석)

순정 재생 화면은 연사 사진을 폴더처럼 한 묶음으로 보여 준다 (PB_BURST_FOLDER_DELETE_FOLDER, UI_PB_Folder_In/Out). 판단 과정:
- di-camera-app UI_Folderview_Check_Folder: 파일 종류가 JPG(1), RAW+JPG(5), SRW(4) 이고, 파일 정보의 연사 상태가 0~2 이며, 앞이나 뒤 파일과 묶음 키가 같으면 묶음 (MPO, 동영상 제외).
- 파일 정보는 libsif ExifDecoder::parseMakerNote 가 메이커노트에서 읽는다. 태그 0x000a (LONG 2개) = (연사 상태, 묶음 키). 태그가 없으면 상태 -1, 키 0 (단사).
- 촬영 때는 libmm-photo CaptureDataParser::convertMakerNote 가 촬영 정보의 연사 상태가 1 이면 새 임의 키(CaptureMess::generateRandomKey)를 만들고, 0~2 면 같은 키를 쓰고, 그 밖이면 키를 지운다. SrwEncoder::putMakerNote 는 상태가 -1 이면 0x000a 를 쓰지 않는다.
- 실기 SRW (단사): 0x000a 없음. 메이커노트 값 위치는 메이커노트 시작 기준 (TIFF 기준 아님). 0x002f 문자열(255바이트)은 첫 바이트만 0 이고 뒤에 "CHK" 블록이 있어 빈 영역이 아님. 값 개수 0 인 항목이 다섯 개 (0x00e0, 0x00e1, 0x00e2, 0x0101, 0x0102).

nxgroup (tools/nxmenu/nxgroup.c): 개수 0 항목 두 개를 빼고 0x000a 를 번호 순서 자리에 넣어 항목 수를 하나 줄이고, IFD 끝에 남는 12바이트에 다음 IFD 위치(0)와 값 8바이트를 쓴다. 파일 크기, 다른 값 위치는 그대로.
- PC: 실기 SRW 사본에서 exiftool 이 0x000a 를 (1, 키), (2, 키) 로 읽음. 바뀐 바이트는 메이커노트 IFD 안의 약 276바이트뿐. exiftool -validate 경고는 원본과 같음. ARM 빌드도 qemu 로 같은 결과.
- 확인할 것: JPEG 메이커노트에도 개수 0 항목이 있는지 (없으면 nxgroup 이 그 파일을 건드리지 않고 log 에 남김), 순정 연사 파일의 0x000a 값 (nxgroup -l), 고친 뒤 재생 목록에 바로 반영되는지 (카메라가 목록을 다시 읽는 시점).
